# JSONL Output Schema

This document defines the JSONL schema for benchmark output files generated by the `web-rwkv` benchmarking runner.

## Overview

Benchmark output consists of a stream of newline-delimited JSON records written to a `.jsonl` file. Each file contains:

1. **One run header record** (`type: "run"`) at the start
2. **Multiple measurement records** (`type: "measure"`), one per (case x repeat)

All records include a `schema_version` field to support forward compatibility.

---

## Schema Version

```
schema_version: 1
```

The schema version is an integer that will be bumped on breaking changes. Consumers should check this field and handle unknown versions gracefully.

---

## Run Header Record

The run header record captures metadata about the benchmark execution environment. It is written once at the start of each benchmark run.

### Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | Always `"run"` |
| `schema_version` | integer | Yes | Schema version (currently `1`) |
| `run_id` | string | Yes | Unique run identifier (timestamp + random suffix, e.g., `"20260128T083000Z_a1b2c3"`) |
| `started_at_utc` | string | Yes | ISO 8601 timestamp when the run started (e.g., `"2026-01-28T08:30:00Z"`) |
| `git_sha` | string | Yes | Git commit SHA of the codebase |
| `git_dirty` | boolean | Yes | `true` if the working directory had uncommitted changes |
| `crate_version` | string | Yes | Version of the `web-rwkv` crate (from `Cargo.toml`) |
| `rustc_version` | string | Yes | Rust compiler version used for the build |
| `host` | object | Yes | Host system information (see below) |
| `gpu` | object | Yes | GPU/adapter information (see below) |
| `uname` | string | No | Full `uname -a` output (optional; preferred over duplicating kernel fields) |

### `host` Object

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `os` | string | Yes | Operating system (e.g., `"linux"`, `"windows"`, `"macos"`) |
| `cpu` | string | Yes | CPU model name (e.g., `"AMD Ryzen 9 7950X"`) |
| `ram_gb` | number | Yes | Total system RAM in gigabytes |

### `gpu` Object

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `adapter_name` | string | Yes | GPU adapter name as reported by the backend (e.g., `"AMD Radeon RX 7900 XTX"`) |
| `backend_api` | string | Yes | Graphics API backend (e.g., `"Vulkan"`, `"Dx12"`, `"Metal"`, `"hip"`) |
| `driver_version` | string | No | Driver version if obtainable |
| `driver_info` | string | No | Additional driver information |

### Example

```json
{
  "type": "run",
  "schema_version": 1,
  "run_id": "20260128T083000Z_a1b2c3",
  "started_at_utc": "2026-01-28T08:30:00Z",
  "git_sha": "d7327a6f1234567890abcdef1234567890abcdef",
  "git_dirty": false,
  "crate_version": "0.8.0",
  "rustc_version": "1.82.0",
  "host": {
    "os": "linux",
    "cpu": "AMD Ryzen 9 7950X 16-Core Processor",
    "ram_gb": 64.0
  },
  "gpu": {
    "adapter_name": "AMD Radeon RX 7900 XTX",
    "backend_api": "Vulkan",
    "driver_version": "24.3.1",
    "driver_info": "Mesa 24.3.1"
  },
  "uname": "Linux hostname 6.12.0-0.rc5.38.fc42.x86_64 #1 SMP PREEMPT_DYNAMIC x86_64 GNU/Linux"
}
```

## Measurement Record

Measurement records capture the results of individual benchmark cases. One record is written per (case x repeat).

### Common Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | Always `"measure"` |
| `schema_version` | integer | Yes | Schema version (currently `1`) |
| `run_id` | string | Yes | Run identifier (matches the run header) |
| `case_id` | string | Yes | Stable case identifier (see [case_id Computation](#case_id-computation)) |
| `repeat_index` | integer | Yes | Zero-based repeat index within this case |
| `scenario` | string | Yes | Benchmark scenario: `"decode_only"`, `"prefill_uniform"`, or `"prefill_mixed"` |
| `status` | string | Yes | Execution status: `"ok"`, `"skipped"`, or `"error"` |
| `error_kind` | string | No | Error classification (only when `status` is not `"ok"`) |
| `error_message` | string | No | Error details (only when `status` is not `"ok"`) |

### Case Identity Fields

These fields identify the benchmark configuration being measured.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `model_id` | string | Yes | SHA256 hash of the model weights file (artifact identity) |
| `model_name` | string | Yes | Human-readable model name (e.g., `"RWKV-x070-World-0.1B-v2.8-20241210-ctx4096"`) |
| `model_path` | string | Yes | Path to the model file |
| `model_size` | string | Yes | Human-readable size label (e.g., `"0.1b"`, `"2.9b"`) |
| `rwkv_version` | string | Yes | RWKV architecture version: `"v4"`, `"v5"`, `"v6"`, or `"v7"` |
| `backend_id` | string | Yes | Backend identifier: `"wgpu"` or `"hip"` |
| `wgpu_backend` | string | Yes | Graphics API (e.g., `"Vulkan"`, `"Dx12"`, `"Metal"`, `"hip"`) |
| `batch_size` | integer | Yes | Batch size for this case |
| `token_chunk_size_requested` | integer | Yes | Requested token chunk size from config |
| `token_chunk_size_effective` | integer | Yes | Effective token chunk size (rounded to multiple of 32) |

### Scenario-Specific Fields

#### For `decode_only` Scenario

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `decode_steps` | integer | Yes | Number of decode steps (token generation iterations) |

#### For `prefill_uniform` Scenario

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `seq_len` | integer | Yes | Uniform sequence length for all sequences in the batch |

#### For `prefill_mixed` Scenario

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `seq_lens` | array[integer] | Yes | Array of sequence lengths (length = `batch_size`) |
| `mixed_case_id` | string | Yes | Identifier for the mixed-length case (e.g., `"short_long_mix"`) |

### Metrics Fields

#### Decode Metrics (for `decode_only` scenario)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `decode_total_ms` | number | Yes | Total time for all decode steps in milliseconds |
| `decode_steps` | integer | Yes | Number of decode steps executed |
| `decode_tokens` | integer | Yes | Total tokens generated (`batch_size * decode_steps`) |
| `decode_tok_per_s` | number | Yes | Decode throughput in tokens per second |
| `decode_step_ms_p50` | number | No | 50th percentile (median) step latency in milliseconds |
| `decode_step_ms_p95` | number | No | 95th percentile step latency in milliseconds |

#### Prefill Metrics (for `prefill_uniform` and `prefill_mixed` scenarios)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `prefill_total_ms` | number | Yes | Total time for prefill in milliseconds |
| `total_prompt_tokens` | integer | Yes | Total tokens processed across all sequences |
| `prefill_tok_per_s` | number | Yes | Prefill throughput in tokens per second |
| `num_infer_calls` | integer | Yes | Number of `infer()` calls made during prefill |
| `ttft_ms_local` | array[number] | Yes | Time to first token per sequence in milliseconds (length = `batch_size`) |
| `ttft_min_ms` | number | Yes | Minimum TTFT across sequences |
| `ttft_p50_ms` | number | Yes | Median TTFT across sequences |
| `ttft_max_ms` | number | Yes | Maximum TTFT across sequences |

## case_id Computation

The `case_id` is a stable identifier for a single benchmark "cell" in the matrix. It is used to:

1. Group repeat measurements together
2. Compare results across different runs
3. Identify regressions or improvements

### Requirements

- **Stable**: The same case configuration must always produce the same `case_id`, regardless of when or where the benchmark runs.
- **Normalized**: Computed from normalized case parameters only. The following are explicitly **excluded**:
  - `run_id`
  - Timestamps (`started_at_utc`, etc.)
  - `adapter_name` (varies by machine)
  - `repeat_index`

### Computation Method

The `case_id` can be computed as either:

1. **Human-readable string** (recommended for debugging): A colon-separated string of key parameters.
2. **Hash of canonical JSON**: SHA256 hash of a canonical JSON encoding of the parameters.

### Parameters Included in case_id

The following parameters define a case:

| Parameter | Description |
|-----------|-------------|
| `scenario` | `"decode_only"`, `"prefill_uniform"`, or `"prefill_mixed"` |
| `model_id` | Model artifact identity (or `model_name` as fallback) |
| `backend_id` | `"wgpu"` or `"hip"` |
| `wgpu_backend` | Graphics API variant |
| `batch_size` | Batch size |
| `token_chunk_size_effective` | Effective chunk size (not requested) |

Plus scenario-specific parameters:

| Scenario | Additional Parameters |
|----------|----------------------|
| `decode_only` | `decode_steps` |
| `prefill_uniform` | `seq_len` |
| `prefill_mixed` | `mixed_case_id`, `seq_lens` (sorted for stability) |

### Human-Readable Format

```
{scenario}:{model_id_short}:{backend_id}:{wgpu_backend}:bs{batch_size}:c{chunk_size}:{scenario_params}
```

Examples:
- Decode: `decode_only:rwkv7_0.1b:wgpu:Vulkan:bs4:c2048:steps100`
- Prefill uniform: `prefill_uniform:rwkv7_0.1b:wgpu:Vulkan:bs4:c2048:len512`
- Prefill mixed: `prefill_mixed:rwkv7_0.1b:wgpu:Vulkan:bs4:c2048:short_long_mix`

### Hash-Based Format

If using a hash, compute as:

```
sha256(canonical_json({
  "scenario": "decode_only",
  "model_id": "sha256:a1b2c3...",
  "backend_id": "wgpu",
  "wgpu_backend": "Vulkan",
  "batch_size": 4,
  "token_chunk_size_effective": 2048,
  "decode_steps": 100
}))
```

The canonical JSON should:
- Sort keys alphabetically
- Use no whitespace
- Encode numbers without trailing decimals

Example hash: `case:sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`

## Status Values

| Status | Description |
|--------|-------------|
| `ok` | Benchmark completed successfully |
| `skipped` | Benchmark was skipped (e.g., unsupported configuration, resource limits exceeded) |
| `error` | Benchmark failed with an error |

### Error Classification

When `status` is `"skipped"` or `"error"`, the following fields provide details:

| Field | Example Values |
|-------|----------------|
| `error_kind` | `"unsupported_backend"`, `"out_of_memory"`, `"timeout"`, `"model_load_failed"`, `"inference_error"` |
| `error_message` | Human-readable error description |

---

## File Naming Convention

Benchmark output files should follow this naming pattern:

```
{run_id}.jsonl
```

Example: `20260128T083000Z_a1b2c3.jsonl`

This ensures:
- Files are naturally sorted by time
- Each file can be uniquely identified
- The run_id in the filename matches the run_id in the records

---

## Validation

Consumers of JSONL output should validate:

1. First record has `type: "run"`
2. All subsequent records have `type: "measure"`
3. All records have matching `schema_version`
4. All measure records have `run_id` matching the run header
5. Required fields are present based on `scenario` and `status`
